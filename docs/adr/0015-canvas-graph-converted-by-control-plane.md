# 画布图经控制面的转换器进入引擎

dsh 现有的工作流是画布图：22 种节点、没有子图、表达式是 JavaScript，不是 Dify DSL 的子集（事实见根目录的 `dsh workflow.md`）。引擎只认 Workflow Definition（ADR-0010）。决定由控制面实现一个转换器，把画布图转成 Workflow Definition：画布照旧编辑画布图，同一个转换器用于存量迁移。画布改为直接编辑 Workflow Definition 是方向，等画布需要编辑 Dify 独有的节点时再做。

引擎不为画布图做两件事。一是不实现画布图的执行器。二是不增加「字符串字段可以写 JS 表达式」的扩展：转换器把导入器生成过的写法还原成 Dify 的结构化写法，还原不了的降级成一个 JS 代码节点，在 JS 沙箱里执行；画布上仍然允许用户写 JS，由转换器负责降级。

## Considered Options

- 引擎再实现一套画布图的执行器：两套执行语义必然漂移。控制面与数据面分离（ADR-0001）要避免的正是这个 → 否决
- 现在就把画布改成直接编辑 Workflow Definition：存量图无论如何都要转换一次；画布重写是独立的大工程，不该阻塞接入 → 本期否决，列为方向
- 引擎增加 JS 表达式扩展，任意字符串字段都可以写 JS：引擎要维护第二套求值语义；Dify 节点的配置里会混进 JS，从画布来的和从 Dify 导入的工作流在引擎里走不同的求值路径 → 否决，画布的表达式体验改由转换器保住

## Consequences

- 引擎的节点类型保持「Dify 的全集加少数扩展节点」，JS 只存在于 code 节点
- 转换器要维护一张「画布节点 → Dify 节点或扩展节点」的映射表和一套降级规则；降级会往定义里插入代码节点，转换后的定义比画布图多出节点
- 这期间在引擎里导入的 Dify 工作流不经画布编辑，因为画布表达不了 Dify 独有的节点
- 转换不了的东西在转换报告里按三级严重度处理（D53，ADR-0014）
